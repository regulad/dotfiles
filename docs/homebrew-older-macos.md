# Homebrew on older macOS

Mainline Homebrew only ships bottles (prebuilt binaries) for the macOS releases it calls Tier 1 -- as of September 2026 that is Sequoia 15, Tahoe 26 and Golden Gate 27, on Apple Silicon only. Everything older, and every Intel Mac, is Tier 3: brew still runs, but each `brew install` is a from-source build with no guarantee it succeeds. Intel is scheduled to stop running brew at all in or after September 2027. The bottles built while a release *was* Tier 1 are still on ghcr.io, though, so an old Mac -- the kind kept around for work newer macOS can't do, like USB sniffing -- is served by brew from that era instead:

- `.chezmoidata/brew-tiers.toml` maps each `(macOS series, arch)` tuple that is no longer Tier 1 (the series is the release as Homebrew names it: `11` and up, or `10.15`) to the last `Homebrew/brew` release tag whose docs still listed it as fully supported, and an era. Each era names one commit per tap, `core_commit` and `cask_commit`: the newest commit at which every formula in the lists still has that host's bottle, which can be weeks or months before the docs demotion, because bottles stop being built for an OS formula by formula. Each entry cites the upstream commit it came from. A tuple absent from the table is Tier 1 and gets mainline brew.
- `005-homebrew` does not use the upstream installer on such a host: no version of it pins a ref, every version ends with `brew update`, current ones refuse Intel and old releases, and older ones clone homebrew-core from a branch that no longer exists. Instead it reproduces the small, stable part of what the installer does -- the prefix directories with their `user:admin` ownership, a git checkout of Homebrew/brew at the era tag, the Intel `bin/brew` symlink -- then lays `homebrew/core` and `homebrew/cask` down itself at their era commits (the JSON API only describes current bottles, so the taps have to be real git checkouts). All three are single-commit, depth-1 fetches by tag or by hash: nothing in the pinned flow needs history, `brew install` reads the formula files in the working tree, and a full homebrew-core clone is well over a gigabyte. `brew doctor` will mention the shallow clones. Every apply re-verifies the pin, repo first with git alone, then the taps.
- `posix-preamble.sh` and `.commonprofile` export `HOMEBREW_NO_AUTO_UPDATE=1` and `HOMEBREW_NO_INSTALL_FROM_API=1` on such a host, so neither a hookscript nor an interactive shell can move brew off the pin or make it read the API.
- `brew_trust` in the preamble wraps `brew trust`, which a 2023-era brew doesn't have; the tap and formula lists work unchanged on both.

## Package lists

The package lists are written against current homebrew-core and homebrew-cask, and adapt themselves to the era inline: each list resolves the era name at the top, and an entry that had a different name at that checkout (`ruby@4` was `ruby`, `handbrake-app` was `handbrake`) or that did not exist there yet (retry and sshpass before 2024, fernflower and git-xet before 2026, a dozen casks such as claude and codex) or whose cask declares a floor or arch the host fails (chatgpt and forklift on Ventura, kde-connect anywhere but Apple Silicon Sonoma) is a template conditional next to the current entry, so the list still reads as one list and nothing is fetched from anywhere but the pinned taps. Everything left is installed from the era's tap commits with bottles. The evidence behind each conditional is the per-era tap audit of 2026-09-28, summarised in the data file's comments. (The deleted homebrew-cask-versions tap was audited through its surviving fork network; GitHub keeps a deleted repository's forks, and a commit SHA identifies the content regardless of which fork serves it.) A cask is only as good as its download URL, and a pinned cask tap keeps pointing at whatever the vendor served in that year, so a second audit the same day resolved every cask's URL at every pin (arch and OS stanzas, version interpolation) and requested each one: bartender (the vendor moved hosts twice; the old `macbartender.com/B2` path 404s), safe-exam-browser (the 3.x GitHub release assets were deleted) and nx-studio (Nikon removed the 2024-25 archive paths) are dead at every pin before 2026 and are gated to the 2026 eras like the rest. grandperspective's SourceForge URLs answer with a Cloudflare challenge to anything that is not a browser, so they could not be verified either way and are left in. A URL that still answers can still fail: a vendor that re-uploads a file under the same name leaves the pinned cask's `sha256` pointing at bytes that no longer exist. Every checksummed cask from element to the end of the Big Sur list was downloaded and hashed (both arches): forklift's unversioned `ForkLift4.zip` no longer matches the 2023 pin and is gated off that era; everything else matches, calibre and prismlauncher included once their per-macOS-version branches are read correctly (a cask with `on_<release>` blocks declares one sha256 per branch, and only the host's branch counts). forklift, prismlauncher and calibre were also hashed at every other era's pin and match there. Casks with `sha256 :no_check` (element, spotify, steam, google-drive) cannot mismatch. The other eras' remaining checksums are not verified.

## The floor

The floor is Catalina (10.15), and it is set by the [bottle mirror](brew-mirror.md). Every era fetches its bottles through the mirror, and Catalina's brew 3.6.6 is the oldest that can: Mojave's 3.2.17 cannot send the Basic auth the mirror requires, and it rewrites every download URL to the mirror, so with the mirror set it could not fetch a source tarball or cask at all. Mojave was an era here, the one host left off the mirror, until 2026-10-04, when it was dropped. Below Mojave, bottle hosting rules a host out regardless. Homebrew moved bottles from Bintray to ghcr.io in April 2021 and copied only the bottle live in each formula at that moment. High Sierra and older were demoted before the move: their era brews only know the dead Bintray URL scheme, and of 30 sampled formulae at their era commits, 6, 1 and 1 still have a bottle on ghcr.io, so even a newer brew that still runs there has nothing left to fetch. Catalina was demoted after the move, so every formula in these lists at its era commit still has a bottle on ghcr.io today (checked blob by blob). `mas install` only re-downloads apps already in the Apple Account's purchase history, so `060-mac-app-store` falls back to `mas purchase` when an install fails, which is how a fresh account gets its free apps. (`mas purchase` is a zero-price purchase; it is `mas get` since 5.x, with the old name kept as an alias.) The Catalina, Big Sur and Monterey pins carry mas 1.8.6, which refuses `purchase` on 10.15+ (1.8.7, November 2024, re-enabled it). On those eras the fallback fails too, and each app has to be gotten once by hand in the App Store; the script says so and moves on. The 2025+ pins are past that block. The same era conditionals reach the tooling scripts. uv and pnpm themselves are installed on every era (uv from MacPorts before 2024, when it reached homebrew-core), but on an era-pinned host nothing is installed *through* them: the `uv tool install` set in `100-python-tooling` and the pnpm global packages in `070-js-tooling` are specialised tooling, not part of the general environment an old Mac is brought up for, and each entry carries a Python or node version story of its own. Both scripts say so and do only their brew installs there; `080-vencord`, which is nothing but a pnpm build, is masked in `.chezmoiignore.tmpl` on such hosts (and refuses to run if invoked by hand). cargo follows the same rule: `020-brew-packages` installs the stable toolchain on every era (through `rustup-init` on the pins where brew's `rustup` is still an alias of it, keyed on the cargo proxy in `~/.cargo/bin` rather than on `~/.cargo` existing, which it always does because `credentials.toml` is managed there), and `110-rust-tooling` skips its from-source `cargo install`s on a pinned host. `120-go-tooling` does the same with its `go install`s; go itself still comes from brew. `160-install-vscode-ext` is masked on such hosts too (the editor cask still installs; the extension set is not applied). Of the brew-installed tools, `typescript-language-server` is absent on Catalina, since it postdates that era's homebrew-core; without the pnpm route it is simply left out.

## `brew update`

`brew update` is the one command that undoes all of this: it moves brew and both taps to upstream HEAD, and on 10.x leaves a brew that will not start. So on an era-pinned host it never runs. The env above stops the implicit one, nothing in this repo runs the explicit one (the upstream installer, which does, is not used on such a host), and `.commonprofile` wraps `brew` so that `brew update` prints a warning and does nothing; `brew! update` is the real binary for when you mean it, after a `git fetch --unshallow` in the brew repo and both taps, since the pinned checkouts are single-commit. If it does get run, the next `chezmoi apply` re-pins: `005-homebrew` resets the brew repo with git alone, by path, before the first `brew` invocation, then the taps.

## Bottle mirror

The bottles the era brews fetch are old blobs on ghcr.io, and nothing obliges GitHub to keep them. Like every brew this repo runs, the era brews fetch them through the Nexus proxy of ghcr.io described in [Bottle mirror](brew-mirror.md), which keeps a copy of each one. That doc covers what each pinned brew does with the mirror variables (none of them falls back to ghcr.io in practice), and how to get past a mirror outage.

## Other caveats

Apple's trust store is frozen with the OS, and it is what the system curl that brew runs verifies against. InCommon, the certificate service behind Internet2 universities' mirrors, moved its issuing chain to emSign in July 2026, so hosts like ftp.osuosl.org, where get.videolan.org redirects the vlc cask, now chain to emSign Root CA - G1 (a 2018 root). Mozilla's bundle has carried it since 2018, and so does every ca-certificates formula in these eras, but Apple only added emSign to the shared trust store that shipped with macOS 13 (store version 2022070700); the macOS 11 store (2020082800) and the last macOS 12 one (2021070500) lack it, and older releases never had it. Any download brew makes to such a host on Catalina through Monterey fails verification. There is a second, unrelated problem with the same system curl on Catalina and Big Sur: it cannot talk to the bottle mirror at all. Apple's curl is a multi-backend build, and Apple's patch to `vtls.c` makes it default to the bundled LibreSSL whenever that library is present (`have_openssl()`), with SecureTransport used only if `CURL_SSL_BACKEND=secure-transport` is set. Those releases ship LibreSSL 2.8.3, which speaks TLS 1.2 at most, and the mirror sits behind Cloudflare with a TLS 1.3 minimum, so every mirror download dies with `tlsv1 alert protocol version` (the server refusing the client's TLS version). Monterey's LibreSSL 3.3 and Ventura's are fine. brew's lighter switch for the trust-store problem, `HOMEBREW_FORCE_BREWED_CA_CERTIFICATES` (the curl shim passes the Mozilla bundle as `--cacert`), does nothing for that, so `brew-era-env.sh` sets brew's other switch, `HOMEBREW_FORCE_BREWED_CURL`, on the three pre-Ventura eras: once the curl formula is installed, brew runs every download through it, and that curl is built on openssl@3 (TLS 1.3) with the ca-certificates bundle as its default trust store, so both problems go away at once. Until it is installed brew falls back to the system curl by itself, so `020-brew-packages` installs curl first on those eras, and for that one install it unsets the mirror variables: ghcr.io still accepts TLS 1.2 and its DigiCert chain is in Apple's store, so the system curl can fetch curl's bottle directly, after which every download goes through brew's curl and the mirror. (Lowering the Cloudflare zone's minimum TLS version to 1.2 would make the detour unnecessary, but the brewed curl is needed for the emSign hosts regardless.) This only fixes brew: Safari and everything else on those releases still distrust the same hosts, which would take adding the root to the System keychain.

Apple's git on Big Sur and older (2.30) predates SSH commit signing, and `gpg.format = ssh` is a value it rejects fatally for every git command, chezmoi's included. `.gitconfig` therefore has no signing block at all under dummy secrets, and with real secrets picks by the version of the git first on PATH when it renders: 2.34 and newer get SSH signing as usual; older gets GPG signing through gpg-agent with the managed key, which `145-gpg-keys` (now on macOS too) imports in the same apply. It re-renders every apply, so once brew's git shadows Apple's the SSH branch returns on its own. Anything that still calls `/usr/bin/git` directly on such a host is on its own.

`brew services` is not built into brew before 4.6, the Ventura era's tag; the earlier brews auto-tap `homebrew/services`, and that archived tap has been emptied down to a README since the command moved into brew, so auto-tapping yields no command. The Catalina, Big Sur and Monterey eras therefore carry a `services_commit` too, and `005-homebrew` lays that tap down like the other two, at its last commit before the era's demotion date, which is the code written for that brew.

Touch ID for sudo (`025-pam-sudo-touchid`) is Sonoma and newer only: that is where `/etc/pam.d/sudo_local` exists, a file that is ours to write and survives OS updates. Older releases would need edits to Apple's own `/etc/pam.d/sudo`, so they are left alone and sudo there is password-only: the script refuses to run below Sonoma, and `.chezmoiignore.tmpl` masks it there as well, so it never appears in the apply. Because OpenPAM refuses the whole chain, and with it every sudo, when a listed module file does not exist, the script runs after `020-brew-packages` provides `pam_reattach.so` and exits 1 rather than write anything if either module it names is missing. There is no `visudo` for PAM to validate a policy with: OpenPAM ships none, and `pamtester`, the usual dynamic check, is not in homebrew-core and does not build on current macOS. When upstream demotes another tuple (next expected: Sequoia 15 on Apple Silicon, September 2027 or later), add it to the table with a new era block; the comments in `brew-tiers.toml` say what to record.

## Bootstrapping a host older than Ventura

chezmoi is a Go program, and every August a Go release drops the oldest macOS it supports. A chezmoi built with a too-new Go does not start on the older release: the dynamic linker dies on a Security.framework symbol the OS does not have (on Big Sur, `_SecTrustCopyCertificateChain`, which is macOS 12 API). The `get.chezmoi.io` script installs the newest release by default, so on these hosts pass the tag of the last release built before the relevant Go cutoff:

| macOS | Go cutoff | chezmoi tag |
| --- | --- | --- |
| 12 Monterey | Go 1.27 (August 2026) requires 13 | `-t v2.72.0` |
| 11 Big Sur | Go 1.25 (August 2025) requires 12 | `-t v2.64.0` |
| 10.15 Catalina | Go 1.23 (August 2024) requires 11 | `-t v2.52.0` |

These are the last releases before each Go version shipped. The toolchain a given binary was built with is not recorded in the release, so if one still fails to start, step back one more release. Once brew is up, the era's pinned `chezmoi` formula is the durable replacement, since its bottle was built for that OS.

`bw` needs no special handling: it is brew's `bitwarden-cli`, installed by the first apply from the era's core checkout, so it is whatever version that era had (a 2022 build on Catalina). Whether a very old client still talks to the current server is not verified here.

## MacPorts

`.chezmoiscripts/00-macos/016-macports` installs the MacPorts CLI (`port`) from the official per-release installer package, latest version, into `/opt/local`. Brew remains the package manager; MacPorts is the fallback for Intel Macs once brew stops running on them (scheduled for September 2027), and on the era-pinned hosts `017-macports-packages` installs the few ports that stand in for formulae the era's homebrew-core checkout does not have and that have a prebuilt MacPorts archive for that Darwin version: retry, sshpass and uv on Catalina and Big Sur. On a Tier 1 host that list is empty. The same inline era conditionals in the brew lists say which entries MacPorts covers. `.commonprofile` puts `/opt/local/bin` and `/opt/local/sbin` ahead of brew's directories on `PATH`, so an installed port wins a collision. The installer's own edits to `~/.zprofile` and `~/.bash_profile` are undone by the next apply, since both files are managed here. MacPorts updates itself with `sudo port selfupdate`.
